# 相关研究工作与参考文献

## 1. 相关研究工作

本项目“面向 Serverless 多模态数据引擎的拓扑无关连续执行”与现有研究主要存在四类联系：**工作流可靠执行、运行时动态迁移、在线状态弹性以及动态资源环境下的持续执行**。现有代表性研究如下。

### 1.1 ExoFlow：面向 DAG 工作流的执行与恢复解耦

Zhuang 等提出 ExoFlow，将 Workflow Execution 与 Recovery Mechanism 解耦，通过 Task Annotation 描述 nondeterminism 等执行语义，从而针对不同任务选择不同的恢复机制，并为 DAG 提供 Exactly-once Execution。

ExoFlow 的重要启示是：**复杂工作流的恢复不一定需要采用统一的 Checkpoint-Restart 机制，而可以利用任务自身语义决定恢复方式。**

但 ExoFlow 主要研究故障恢复语义，并未解决运行过程中因 Serverless Scale-in/out、资源整理等导致的**物理执行拓扑持续变化问题**。本项目将在此基础上进一步研究 Logical Execution State 与 Physical Execution Topology 的解耦。

---

### 1.2 GRANNY：通过细粒度执行单元实现应用迁移与资源去碎片化

Segarra 等在 NSDI 2025 提出 GRANNY，使用基于 WebAssembly 的 Granule 执行抽象，将传统多线程和多进程应用拆分成可独立管理、快照和迁移的细粒度执行单元。

GRANNY 支持应用在运行过程中进行纵向扩展以及跨 VM 横向迁移，其实验表明，对于 MPI 工作负载可以降低最高约 25% 的资源碎片。

GRANNY 说明了：

> **正在运行的应用可以主动迁移，以实现集群资源重新整理，而无需等待应用自然结束。**

这与本项目 Serverless Elastic Compaction 的产品目标高度相关。但 GRANNY 的研究对象主要是 OpenMP/MPI 等通用计算程序，其迁移单位仍然接近通用运行时执行上下文。本项目关注的是包含 Operator、Partition、Data Object、Model Runtime 和 Dataflow Progress 的**数据流逻辑执行状态**。

---

### 1.3 Quicksand：利用可 Split/Merge/Migrate 的细粒度计算单元适应动态资源

Ruan 等在 NSDI 2025 提出 Quicksand，用于利用数据中心中短暂存在的 stranded resources。Quicksand 提出 Resource Proclet 抽象，并支持 Proclet 在毫秒级完成 Split、Merge 和 Migration。

该工作的核心思想是：

> **不要要求底层资源长期稳定，而应让应用自身快速适应资源可用性的变化。**

这一思想与本项目提出的“资源形态持续变化时应用本身仍然能够持续执行”高度一致。

不同之处在于，Quicksand 主要解决细粒度 Compute Resource 的管理问题；本项目进一步关注复杂 Dataflow 中存在的 Data State、Progress State、Operator State、大对象及 AI Model State，并需要处理拓扑变化过程中的数据一致性和执行进度连续性。

---

### 1.4 Fugue：Stateful Stream Processing 的在线弹性与状态迁移

Zhang、Mao 和 Jacobsen 在 VLDB 2026 提出 Fugue，针对 Stateful Stream Processing 中传统 Stop-the-world 扩缩容带来的长时间暂停问题，提出两阶段在线弹性协议。

Fugue 首先在后台预迁移大部分 Operator State，随后利用轻量 Barrier 完成最终 State Ownership Cutover，并与 Flink 原有 Exactly-once 同步机制结合。

论文报告，相比 Flink 原生机制，Fugue 对运行中 Query 的重配置速度最高提升约 40 倍，并能够在重配置过程中维持超过 95% 的峰值吞吐。

Fugue 对本项目最重要的启示是：

> **State Migration 不需要位于执行关键路径上，大量状态可以提前迁移，真正影响执行停顿时间的只是最终 Ownership Cutover。**

但 Fugue 的核心状态类型是 Stateful Streaming 中的 Operator/Keyed State。本项目面对的多模态数据流包含大量**可重计算中间数据、大对象、AI Operator、模型 Runtime 以及阶段化 Batch Progress**，其 State Profile 和迁移决策空间明显不同。

---

### 1.5 Styx：Serverless Stateful Function 的在线状态迁移

Psarakis 等提出 Styx，这是一种面向 Stateful Function-as-a-Service 的 Dataflow Runtime，提供 Serializable Transaction 和 Exactly-once Execution。

其后续工作进一步研究 Styx 的在线 State Migration，使系统能够在 Scale-up 和 Scale-down 过程中迁移 Function State，同时维持事务执行和低延迟，而不依赖传统的停止—迁移—重新启动机制。

Styx 表明：

> **Serverless Stateful Application 可以在维持一致性语义的情况下进行在线资源重配置。**

本项目与其区别在于，研究对象从 Transactional Function State 扩展到大型多模态 Dataflow 中的 Execution Progress、Partition、Model Runtime 和 Large Object 等更加复杂的执行状态。

---

### 1.6 TrainMover：大型 ML Training 的中断无感迁移与恢复

Lao 等在 OSDI 2026 提出 TrainMover，针对大型分布式训练频繁遭遇机器故障、维护和管理事件的问题，研究 interruption-resilient ML runtime。

TrainMover 不依赖传统的完整 Checkpoint-Restart，而是利用弹性机器和 Standby Machine，通过增量式通信组建立、Sandbox Warmup 和 Standby Recovery 等机制降低迁移停顿。

其论文报告，在 1024 GPU 环境下处理不同类型中断时，停顿时间可以稳定在约 20 秒。

TrainMover的重要启示在于：

> **对于昂贵的长期运行作业，系统应把资源中断视为正常运行事件，而不是异常结束事件。**

但大型同步训练通常具有相对固定的 Model State 和 Parallelism Semantics，而多模态 Dataflow 的状态更加松散，同时具有大量可重新计算或重新绑定的数据状态。因此，本项目研究的核心不是 Training State Recovery，而是 **Dataflow Logical State Rebinding**。

---

### 1.7 SPADE：动态资源供给条件下的数据处理 DAG 调度

Lechowicz 等在 OSDI 2026 提出 SPADE，研究计算资源供给随时间变化情况下的 Batch Data Processing。

SPADE 同时考虑 DAG 结构和能源价格、碳强度、电力供给等动态外部信号，联合进行资源 Provisioning 和 Task Scheduling。其 Spark 原型在 100 节点 Kubernetes 集群上的实验说明，Batch DAG 的执行策略可以主动适应随时间变化的资源可用量。

SPADE 与本项目存在非常重要的互补关系：

SPADE主要回答：

> **资源变化时，任务应该什么时候、在哪里执行？**

本项目进一步回答：

> **一个任务已经开始执行后，如果底层资源拓扑继续变化，如何保持该 Dataflow 连续执行？**

因此可以分别理解为：

**Dynamic Scheduling / Provisioning**

与：

**Dynamic Execution Reconfiguration**。

---

### 1.8 Dandelion：重新设计 Cloud-native Runtime 以获得真正的云弹性

Kuchler 等在 SOSP 2025 提出 Dandelion，指出即使现代 Serverless/FaaS 平台已经能够快速创建 Sandbox，传统 POSIX 风格运行环境及其资源依赖仍然限制了云平台的真正弹性。

Dandelion通过重新设计 Cloud-native Application Abstraction，将应用表达为 Pure Compute Function 和 Communication Function 组成的 DAG，使运行时能够使用更加轻量级的 Sandbox 按需创建执行环境。

论文实验显示，在 Azure Functions Trace 上，其方案能够将 committed memory 平均降低约 96%。

Dandelion对本项目更深层的启示是：

> **如果希望获得真正的 Serverless Elasticity，仅优化资源调度往往不够，还需要重新设计应用与物理资源之间的执行抽象。**

本项目沿着类似思路进一步研究：

**Logical Dataflow Execution 是否可以从 Physical Worker/Actor Topology 中解耦。**

# 2. 与本项目的研究关系总结

上述工作可以形成如下研究演进关系：

**ExoFlow**

解决：

> 执行与恢复机制如何解耦。

↓

**GRANNY / Quicksand**

解决：

> 应用执行单元如何细粒度迁移，从而利用动态或碎片化资源。

↓

**Fugue / Styx**

解决：

> Stateful Stream / Stateful Function 如何在运行中迁移状态并保持一致性。

↓

**TrainMover**

解决：

> 超大规模长期 ML 作业如何将机器中断转化为运行时可处理的正常事件。

↓

**SPADE**

解决：

> Batch Dataflow 如何适应随时间变化的资源供给。

↓

本项目进一步研究：

> **一个包含大量可重计算 Data State、昂贵 AI Operator、大对象、异构资源和复杂 DAG 的多模态数据处理作业，如何将 Logical Execution State 与 Physical Execution Topology 解耦，使其可以随着 Serverless 资源形态持续变化而保持连续执行。**

因此，本项目的预期研究空白可以进一步概括为：

**Topology-independent Continuous Execution for Multimodal Dataflows**

其研究核心不再是单独的 Migration、Checkpoint 或 Autoscaling，而是三者背后的统一执行抽象：

**Logical Execution State → Online Reconfiguration → State Rebinding → Continuous Execution。**

> 近年来，分布式系统研究正在从传统的故障后 Checkpoint-Restart 逐步演进到运行时状态迁移和动态执行重构。ExoFlow [1] 探索了工作流执行与恢复机制解耦；GRANNY [2] 和 Quicksand [3] 通过细粒度执行单元支持运行中应用迁移和动态资源利用；Fugue [4] 与 Styx [5] 分别研究了 Stateful Stream Processing 和 Stateful Serverless Function 的在线状态迁移；TrainMover [6] 将长期运行的 ML Training 中断转化为运行时可处理事件；SPADE [7] 则进一步研究了 Batch Dataflow 如何适应持续变化的计算资源。与此同时，Dandelion [8] 表明，为获得真正的 Cloud-native Elasticity，需要重新审视应用与底层物理资源之间的执行抽象。本项目在上述研究基础上进一步关注尚未得到充分解决的多模态 AI Dataflow 场景，研究 Logical Execution State 与 Physical Execution Topology 解耦，以及资源形态变化过程中 Dataflow 的连续执行问题。
