英文名称暂定为：**Runtime Topology Reconfiguration and Continuous Migration for Serverless Multimodal Data Processing**

本课题重点研究的不是传统意义上的资源调度或弹性扩缩容，而是：

> **当底层计算资源数量、位置或形态发生变化时，如何对已经运行中的多模态数据处理作业进行执行状态重构和在线迁移，使作业能够在新的资源拓扑上连续执行，而无需整体停止和重新启动。**

# 2. 项目背景

## 2.1 从“资源能够弹性变化”进一步走向“运行中的作业能够随资源变化”

Serverless 云平台的核心目标之一，是根据业务负载动态提供计算资源，从而减少长期资源预留，提高集群整体资源利用率。目前多数弹性技术主要解决的是：
- 根据负载增加或减少计算资源；
- 根据 Operator 特征进行资源调度；
- 通过算子融合减少调度和数据交换开销；
- 通过 Actor Pool 等机制实现计算资源复用和动态扩缩。

这些技术主要回答：

> **一个作业应该使用多少资源，以及资源应该如何高效组织。**

但对于持续数小时甚至数天运行的大规模数据处理作业，仅仅能够调整资源供给仍然不够。

一个正在运行的分布式作业，其 Task、Actor、Partition、中间数据以及运行状态通常已经分散在特定节点之上。当 Serverless 平台因为负载下降、集群资源整理、节点维护或资源回收而需要改变物理资源拓扑时，即使新的资源规模已经足够承载剩余计算，系统仍可能因为已有执行状态绑定在原节点上而无法直接释放资源。

因此容易出现：**业务负载已经下降，但节点无法回收；计算资源已经碎片化，但长作业无法重新聚合；平台具备弹性能力，但运行中的应用本身不具备弹性。**

这成为 Serverless 数据处理进一步提高资源利用率的重要限制。本课题希望研究的核心问题因此不是传统的 Autoscaling，而是：

> **如何使正在运行中的复杂数据处理作业具备随物理资源拓扑变化而持续演进的能力。**

即从：**Resource Elasticity**
进一步走向：**Execution Elasticity**。

# 3. 场景选择：多模态数据处理为什么是该问题的典型场景

本课题选择大规模多模态数据处理作为主要研究对象。典型多模态数据处理流程可能包含：
**数据读取 → 图片/视频解码 → OCR/ASR → VLM/LLM 推理 → Embedding → 数据过滤 → Shuffle/Join → 向量构建 → 数据输出。**

该场景具有几个区别于传统批处理和大模型训练的重要特征。
首先，多模态数据处理通常是**长时间运行的多阶段 Dataflow**。单个作业可能持续数小时甚至更长时间，不同执行阶段的计算量和资源需求变化明显，因此容易在作业运行后期形成大量低利用率节点。
其次，Pipeline 中同时存在**轻量数据处理算子与昂贵 AI 算子**。例如 Decode、Filter 的重计算成本很低，而 VLM、LLM、Embedding 等阶段可能已经消耗大量 GPU/NPU 时间。因此发生资源变化时，简单终止和重新执行会造成较大的重复计算损失。
第三，多模态数据流具有复杂的运行状态。其状态不仅包括传统 Operator State，还可能包括：
- Sample / Block 处理进度；
- Partition 状态；
- Shuffle 中间数据；
- 图片、视频、Tensor 等大对象；
- Object Reference；
- Model/UDF Runtime；
- 已完成的高成本模型推理结果。
因此其迁移问题不能简单退化为传统进程迁移或完整内存快照。

第四，多模态数据处理具有较强的**拓扑可塑性**。与大规模同步训练不同，多模态 Dataflow 通常不要求固定 Worker 数量长期保持不变。同一个逻辑 Pipeline 可以在：**16 个 Worker、8 个 Worker，甚至重新划分后的另一组 Worker**上继续执行。这意味着该场景非常适合研究：

> **Logical Dataflow 与 Physical Execution Topology 解耦。**

多模态数据处理具有传统 Stateful Stream Processing 和大型分布式 AI Training 两类系统的部分特征，但又并不完全属于其中任何一种。它既具有 Dataflow 的 Partition、Shuffle 和执行进度问题，又具有 AI Operator、大对象、异构计算和高重计算成本问题，因此为研究动态资源环境下的连续执行提供了一个具有代表性的研究场景。

> **它既具有 Batch/Dataflow 的大量可重算数据状态，又具有 AI Pipeline 中昂贵的模型执行状态和异构资源依赖。**

近年来相关系统研究已经分别在相邻方向取得进展：ExoFlow 研究了工作流执行与恢复解耦；NSDI'25 的 GRANNY 与 Quicksand 分别研究了细粒度应用迁移和碎片资源利用；VLDB 2026 的 Fugue 研究运行中 Stateful Stream Processing 的在线状态迁移；OSDI'26 的 TrainMover 研究大型训练作业受到中断后的快速恢复；SPADE 则开始研究资源供给持续变化情况下 Batch DAG 的动态调度。

# 4.课题面临的三个关键技术挑战

面向 Serverless 多模态数据处理的动态迁移，并不是简单将一个正在运行的 Actor 或进程从节点 A 搬迁到节点 B。多模态作业运行过程中同时存在处理进度、Operator 状态、Partition、Shuffle 中间结果、大对象引用、模型 Runtime 以及高成本 AI 计算结果等多种状态，这些状态又与具体 Worker、Actor 和数据位置形成复杂依赖。与此同时，Serverless 环境中的资源变化往往意味着 Worker 数量、并行度甚至资源组成发生改变，因此作业需要从执行拓扑 (T_0) 演进到完全不同的 (T_1)，而不是简单完成一对一的节点替换。

因此，本课题的技术难点不能停留在 Checkpoint、Actor Restart 或 State Copy，而需要解决三个具有较强学术挑战、同时又直接决定动态迁移竞争力的核心问题。

## 挑战一：拓扑无关的执行状态解耦与细粒度续作——解决作业“迁得走”

动态迁移首先要解决的并不是“状态怎么搬”，而是**一个已经运行到任意位置的多模态 Dataflow，究竟需要保留哪些状态，才能脱离原有 Worker、Actor 和节点后，在新的资源拓扑上从原有进度继续执行。**

传统进程迁移通常保存进程内存、寄存器等物理运行状态，而传统数据系统 Checkpoint 更多保存 Operator State 或粗粒度执行进度。这两种方式都难以直接适应多模态 Dataflow。多模态作业既包含必须保留的处理进度和高成本 AI 计算结果，也包含大量可以重新计算的临时数据、能够从共享存储重新获得的大对象，以及可以在目标节点重新创建的模型和 UDF Runtime。如果将所有状态完整迁移，会产生很高的迁移成本；如果仅保存粗粒度 Checkpoint，又可能造成大量重复计算。

因此，需要建立一种**与 Worker、Actor 和数据物理位置解耦的 Logical Execution State Model**，从 Dataflow 语义出发描述 Operator、Partition、数据对象、执行进度和 Output Commit 之间的关系，并进一步识别支持作业继续执行所必需的“最小充分状态”。

其核心科学问题是：

> **如何从复杂运行状态中提取支持 Dataflow 正确续作的最小逻辑执行状态，并使其生命周期独立于具体 Worker、Actor 和节点，从而支持执行状态在不同物理拓扑之间重新绑定？**

该问题最终需要形成一套**Topology-independent Execution State & Fine-grained Continuation** 机制。它决定了动态迁移能否摆脱传统进程复制和完整 Checkpoint-Restore，成为真正面向 Dataflow 的执行迁移能力。

---

## 挑战二：低停顿的一致性在线迁移与执行拓扑重构——解决作业“迁得稳”

能够提取执行状态并不意味着已经解决动态迁移。更困难的问题在于：**如何在作业仍然运行、上下游仍然处理数据的过程中，将 Dataflow 从旧执行拓扑 (T_0) 一致地切换到新执行拓扑 (T_1)，同时避免长时间 Stop-the-world。**

例如，当 16 个 Worker 收缩为 6 个 Worker 时，原有 Partition 需要 Merge 和重新映射；当 4 个 Worker 扩展为 12 个 Worker 时，又需要执行 Split。与此同时，旧 Actor 上可能仍然存在正在运行的 Task、尚未消费的数据、正在传输的 Shuffle 数据以及已经产生但尚未提交的结果。迁移过程中，新旧 Actor 还可能短暂共存。

如果缺少严格的一致性协议，就可能产生数据重复执行、数据丢失、状态被多个实例同时修改、上下游路由版本不一致以及已提交结果重复产生等问题。

因此，需要研究一种面向多模态 Dataflow 的 **Non-stop Consistent Reconfiguration Protocol**，使状态准备、Partition Split/Merge、Ownership 转移、Routing Cutover 和 Output Commit 能够协调完成，并将真正需要暂停的时间压缩到很小范围。

其核心科学问题是：

> **如何允许运行中的 Dataflow 在 Worker 数量、并行度和 Partition 布局发生变化时进行在线拓扑重构，同时保证迁移前后数据不丢失、不重复、执行进度一致，并使全局暂停时间尽可能与总状态规模解耦？**

该问题最终对应 **Low-pause Consistent Online Migration**。它决定了动态迁移能否从传统“停止—保存—恢复”模式升级为真正的在线迁移，也是本课题区别于普通 Actor Migration 和 Checkpoint-Restart 的关键技术竞争力。

---

## 挑战三：计算价值感知的低放大状态迁移与重绑定——解决作业“迁得值”

对于大规模多模态 Dataflow，动态迁移还面临一个非常现实的问题：**能够迁移，并不代表值得迁移。**

不同运行状态的大小和计算价值差异巨大。例如，一个 Decode Buffer 可能很快即可重新生成，将其跨网络迁移反而比重算更昂贵；一个已经完成的 VLM 或 LLM 推理结果虽然数据量并不大，但重新计算可能消耗大量 GPU/NPU 时间，应优先保留；几十 GB 的模型权重虽然很大，却未必应该随着 Actor 一起迁移，而可以在目标节点通过共享 Cache 重新加载；已经位于分布式 Cache 中的大 Tensor 则可能完全不需要搬移，只需要重新建立引用和 Ownership。

因此，动态迁移不能简单等价于 State Copy，而应该针对不同状态，在 **Transfer、Recompute、Reload、Remote Retain、Lazy Fetch 和 Rebind** 等方式之间进行选择。

这使迁移问题进一步演化为一个多目标优化问题，需要同时考虑：

状态大小、网络带宽、数据位置、缓存命中率、模型加载成本、重计算成本、DAG 关键路径、迁移停顿以及节点释放收益。

其核心科学问题是：

> **在满足迁移一致性和资源回收时限的前提下，如何依据状态的计算价值和数据位置，自适应决定哪些状态需要迁移、哪些状态应该重算、哪些状态只需要重新加载或重新绑定，从而最小化数据搬移、执行暂停和重复计算的综合代价？**

该问题最终对应 **Cost-aware Migration, Recompute and State Rebinding**。其目标不是把所有状态都搬走，而是做到：

> **只搬必须搬的状态，只重算值得重算的状态，只重新加载可以低成本恢复的状态。**

这决定了动态迁移在大规模多模态作业中是否真正能够产生净收益，而不是用新的网络和迁移开销替代原有的资源浪费。

# 研究内容与关键技术

围绕“运行中的多模态 Dataflow 如何随底层资源拓扑变化持续演进”这一核心问题，本课题拟从**执行状态解耦、在线一致性迁移、低放大迁移决策以及 Serverless 资源压缩**四个方面开展研究。前三项形成课题的核心学术创新，第四项用于将前述机制集成为完整系统，并验证其对 Serverless 弹性和资源利用率的实际价值。

## 研究内容一：拓扑无关的逻辑执行状态与细粒度续作机制

动态迁移首先需要打破 Dataflow 执行状态与具体 Worker、Actor 和节点之间的绑定关系。本研究拟从多模态 Dataflow 的执行语义出发，对运行过程中形成的状态进行系统建模，将传统以进程、Actor 内存为中心的物理状态表示，转化为以 **Operator、Partition、Data Object、Progress 和 Commit State** 为核心的逻辑执行状态表示。

重点研究运行状态的可迁移属性和依赖关系，将状态区分为必须持久化的核心状态、可通过输入重新计算的状态、可从共享存储重新获取的外部状态以及可在目标节点重新构建的 Runtime 状态，并进一步研究支持 Dataflow 正确续作所需的**最小充分执行状态**。在此基础上，构建轻量化的 **Execution Capsule**，用统一方式描述一个执行单元的逻辑身份、数据处理进度、状态依赖、对象引用和提交边界，使其能够脱离原有 Actor 生命周期独立存在，并重新绑定到新的执行实例。

该部分不仅研究如何保存状态，更需要形式化定义 Execution Capsule 的正确性条件，包括状态完整性、处理进度连续性、依赖可恢复性以及输出提交一致性，并研究不同 Operator 类型下最小可续状态的构成差异。最终形成一种**Topology-independent Logical Execution State Abstraction**，使动态迁移从传统的“搬进程”转变为“迁移和重绑定逻辑执行状态”。

其核心技术竞争力在于：**不再要求物理运行环境长期稳定，而是使作业执行进度本身成为可以跨 Worker、跨节点持续存在的一等运行时对象。**

---

## 研究内容二：面向执行拓扑变化的低停顿一致性在线迁移协议

在实现逻辑执行状态解耦后，需要进一步解决正在运行的 Dataflow 如何从拓扑 (T_0) 在线演进到拓扑 (T_1)。与传统故障恢复不同，迁移发生时旧拓扑仍然持续执行，上下游仍有数据流动，同时 Worker 数量、Operator Parallelism 和 Partition Mapping 均可能发生变化，因此本研究重点解决**迁移过程中的执行一致性与连续性问题**。

研究首先建立面向 Dataflow 的拓扑变化模型，支持 Worker 动态增加或减少以及 Operator Partition 的 Split、Merge 和 Remapping。在此基础上研究 Migration Point 与迁移一致性边界，将迁移过程拆分为后台状态准备、目标执行实例建立、增量状态同步、Ownership 转移、Routing Cutover 和旧实例回收等阶段，使大量状态准备工作能够与正常计算并行进行，将最终需要暂停的操作压缩到最小范围。

针对迁移过程中存在的 Pending Task、在途 Shuffle 数据、尚未消费的数据以及已经产生但尚未 Commit 的输出，需要进一步研究统一的**执行权与状态所有权切换协议**，确保迁移过程中任一 Logical Partition 在任一时刻只有明确的有效执行者，并保证数据不丢失、不重复提交。同时研究迁移前后 Object Reference、上游 Routing 和下游消费关系的重新绑定，使执行拓扑变化对于整个 Logical Dataflow 尽可能透明。

最终形成一种 **Low-pause Consistent Online Migration Protocol**，使动态迁移不再依赖完整的：

**Stop → Checkpoint → Restart → Restore**

过程，而能够实现：

**Prepare → Incremental Transfer → Atomic Cutover → Continue**

其核心技术竞争力在于：**让拓扑变化成为 Dataflow 正常运行过程中的一类在线事件，并使迁移暂停时间尽可能由最终切换状态决定，而不是由整个作业状态规模决定。**

---

## 研究内容三：计算价值感知的低放大状态迁移与重绑定优化

多模态 Dataflow 中不同运行状态的数据规模、位置和重计算成本存在显著差异，因此不能采用“一律搬迁”的传统 State Migration 策略。本研究拟进一步将动态迁移建模为一个**状态迁移、重计算、重新加载和重新绑定的联合优化问题**。

首先建立多模态 Dataflow 的状态价值模型，从状态大小、重计算时间、网络传输成本、模型加载成本、Cache 数据位置、下游依赖关系以及 DAG 关键路径等多个维度描述不同运行状态的迁移价值。例如，对于重计算代价很低的 Decode 临时状态优先选择 Recompute；对于已经完成的高成本 VLM/LLM 结果优先保留；对于模型权重优先从共享 Cache Reload；对于已经存在于分布式存储中的大对象则优先采用 Reference Rebinding 或 Lazy Fetch。

在此基础上研究 **Transfer / Recompute / Reload / Remote Retain / Lazy Fetch / Rebind** 等多种恢复方式的联合决策，并建立以迁移暂停、数据搬移量、重复计算量和节点释放时间为目标的 Cost Model。进一步结合 DAG 结构研究迁移优先级和关键路径感知策略，避免大规模节点收缩时所有状态同时搬迁造成网络和存储瞬时拥塞。

该研究最终希望形成一种 **Cost-aware State Migration & Rebinding Planner**，使系统不是简单回答“这个状态能不能迁移”，而是回答：

> **对于当前资源环境和作业状态，采用哪种状态处置方式能够以最低综合代价完成拓扑变化。**

最终目标是显著降低 **Migration Amplification**，做到“只搬必须搬的状态，只重算值得重算的状态，只重新加载可以低成本恢复的状态”。

其核心技术竞争力在于：**将多模态 AI 计算结果的“计算价值”引入迁移决策，使动态迁移从数据搬运问题提升为 Dataflow 语义、计算代价和数据局部性的联合优化问题。**

---

## 研究内容四：面向 Serverless 的运行中资源压缩与弹性执行机制

前三项研究解决动态迁移本身的核心机制，本部分进一步研究如何利用这些机制解决 Serverless 环境中长作业造成的资源碎片和节点无法及时回收问题。

传统 Autoscaling 更多解决资源供给规模调整问题。当多模态长作业进入尾部阶段后，即使逻辑计算需求已经显著下降，只要剩余 Actor、Partition 或执行状态仍然分散在大量节点上，平台仍无法真正释放这些节点。因此，本研究进一步提出 **Elastic Execution Compaction**：在作业仍持续运行的情况下，对其执行拓扑主动进行重构，将分散的 Logical Execution State 向更少的物理节点重新聚合，从而提前释放完整节点。

研究将探索资源压缩过程中的执行单元选择、迁移批次控制、节点释放顺序以及迁移与正常任务调度之间的协同机制，并研究如何将动态迁移能力与 Serverless Scale-in、节点维护、Spot 资源回收以及故障恢复统一到同一种执行拓扑变化模型中。

从系统角度，希望实现：

**负载变化 → 确定目标资源拓扑 → 运行中状态重构 → 执行状态重新绑定 → 节点释放**

而不是传统的：

**负载变化 → 等待任务结束 → 节点释放。**

该部分重点验证前三项研究能否真正转化为 Serverless 系统收益，主要关注 Reconfiguration Pause、Recomputation Ratio、Migration Amplification、Resource Reclaim Time 和 Cluster Utilization 等指标。

其最终目标不是单纯增加一种“作业迁移功能”，而是建立一种新的 **Elastic Execution Runtime**：

> **资源可以根据业务负载变化，运行中的 Dataflow 也能够随资源形态重新塑造自身执行拓扑。**

---

## 核心技术链路

四项研究形成从运行时抽象到系统价值的完整技术链路：

**Topology-independent Execution State**  
解决“什么能够迁移和续作”；

↓

**Low-pause Consistent Online Migration**  
解决“运行中的 Dataflow 如何安全迁移”；

↓

**Cost-aware State Migration & Rebinding**  
解决“如何以最低代价完成迁移”；

↓

**Serverless Elastic Execution Compaction**  
解决“如何利用动态迁移实现资源及时回收和利用率提升”。

因此，本课题的技术核心并不是传统意义上的 Checkpoint、Actor Migration 或 Autoscaling，而是研究一种能够让**逻辑执行进度独立于物理执行拓扑，并在运行过程中低成本、一致地重新绑定到底层资源**的新型 Dataflow Runtime。这也是课题相对于传统进程迁移、状态流迁移和简单弹性调度最主要的技术竞争力。

# 8. 与现有研究的关系及拟突破点

现有相关研究已经分别验证了若干重要方向。

ExoFlow 表明执行机制与恢复机制可以解耦，并针对不同 Task 采用不同恢复策略。

GRANNY 利用细粒度执行抽象支持应用在不同 VM 之间迁移，并在实验中降低多进程工作负载产生的资源碎片。

Quicksand 通过能够快速 split、merge、migrate 的细粒度 Resource Proclet 利用数据中心中的碎片资源。

Fugue 针对 Stateful Stream Processing 提出了低暂停在线弹性机制。

TrainMover 则针对大型分布式训练提出 interruption-resilient runtime，在 1024 GPU 环境中报告约 20 秒级中断处理时间。

SPADE 进一步表明 Batch Data Processing 也需要开始适应随时间变化的计算资源供给。

本项目不重复研究通用进程迁移、传统 Stream State Migration 或 Training State Recovery，而聚焦一个尚未被上述工作完整覆盖的问题：

> **针对包含大量可重算数据、昂贵 AI Operator、大对象和异构执行资源的多模态 Dataflow，研究 Logical Execution State 与 Physical Execution Topology 解耦，以及运行中 Dataflow 的低成本在线拓扑演进。**

拟形成的差异包括：

1. 从 **Process State** 转向 **Logical Dataflow State**；
    
2. 从 **State Transfer** 转向 **State Rebinding + Selective Recompute**；
    
3. 从一对一 Migration 转向 **Execution Topology Reshaping**；
    
4. 从 Failure Recovery 扩展到 **Serverless Continuous Elasticity**；
    
5. 从停止式 Rescale 转向 **Online Continuous Execution**。

# 11. 实验场景设计

重点设计四类 Topology Change。

## 场景一：主动 Scale-in

例如：

```
32 Worker
   ↓
16 Worker
   ↓
8 Worker
```

验证：

运行中的长作业是否能够持续执行。

---

## 场景二：动态 Scale-out

```
4 Worker
    ↓
16 Worker
```

验证：

是否能够在线 Split Execution State，并利用新增资源。

---

## 场景三：Serverless Resource Compaction

制造集群碎片：

```
Node A  ██████░░
Node B  █████░░░
Node C  ██░░░░░░
Node D  █░░░░░░░
```

通过迁移：

```
Node A  ████████
Node B  ███████░
Node C  RELEASE
Node D  RELEASE
```

验证：

是否真正提升节点回收能力。

---

## 场景四：节点故障 / Preemption

运行中随机撤销节点。

验证：

同一 Execution State Abstraction 是否能够同时支持：

- Elastic Migration；
    
- Failure Recovery；
    
- Serverless Reclaim。
    

如果可以，将进一步证明该抽象的通用性。

# 12. 评价指标

本项目不以单一 Recovery Time 作为评价标准。

建议建立以下指标体系。

## 12.1 Reconfiguration Pause

从拓扑切换开始到 Dataflow 恢复正常处理的时间。

研究目标建议：

**常规 Scale-in/out 场景达到 1～5 秒级 Pause。**

具体目标在完成基线实验后进一步校准。

---

## 12.2 Recomputation Ratio

定义：

**拓扑变化造成的重复计算量 / 已完成计算量**

重点验证昂贵 AI Operator 是否可以避免大规模重复执行。

研究目标建议：

**典型场景低于 1%。**

---

## 12.3 Migration Amplification

定义：

**实际搬移的数据量 / 理论必须保存的状态量**

用于评价 Execution Capsule 与 State Rebinding 是否真正降低迁移量。

---

## 12.4 Steady-state Overhead

即在没有发生迁移时，支持动态迁移能力本身造成的性能开销。

研究目标建议：

**稳态吞吐影响控制在 5% 以内。**

---

## 12.5 Resource Reclaim Time

从平台决定 Scale-in 到目标节点真正能够释放的时间。

这是 Serverless 产品最重要的系统指标之一。

---

## 12.6 Resource Utilization

对比：

**No Migration / Checkpoint-Restart / Topology-independent Execution**

在长作业和尾部阶段的：

- CPU 利用率；
    
- GPU/NPU 利用率；
    
- Cluster Utilization；
    
- Node Fragmentation。
    

建议以相对传统调度方案：

**集群有效资源利用率提升 15%～30%**

作为研究目标区间，最终值依据真实基线确定。

---

## 12.7 Correctness

必须验证：

- No Data Loss；
    
- No Duplicate Commit；
    
- Progress Consistency；
    
- Partition Ownership Consistency；
    
- 拓扑变化前后结果一致性。
    

---

# 13. Baseline

建议至少对比：

### Baseline 1：No Migration

等待作业自然结束后才能释放资源。

### Baseline 2：Job Restart

终止作业，在新资源上从头运行。

### Baseline 3：Checkpoint-Restart

Checkpoint 后重新启动。

### Baseline 4：Ray Native Mechanisms

利用 Ray 现有 Task Retry、Actor Restart、Ray Data Checkpoint 等机制。

### Baseline 5：State Migration 类方案

在可比较场景下选择 Stateful Stream Processing / Existing Migration Method 作为学术对比对象。

# 17. 项目成功判据

项目是否成功，不应仅用“是否完成动态迁移功能”判断。

真正的研究成功应回答以下问题：

### 1.

是否提出了一种清晰、可复用的：

**Topology-independent Execution State Abstraction？**

### 2.

是否证明一个正在运行的复杂 Dataflow 可以从：

**Topology T₀**

在线转化为：

**Topology T₁**

而无需整体重新启动？

### 3.

是否能够显著降低传统 Checkpoint-Restart 带来的：

**Pause、State Transfer 和 Recomputation？**

### 4.

是否能够利用这一能力真正解决 Serverless 环境中的：

**Resource Fragmentation 和 Long-running Job Scale-in？**

### 5.

该机制是否能够统一支持：

**Elastic Scaling + Job Migration + Failure Recovery + Resource Reclaim？**

如果上述问题能够得到肯定回答，则说明项目形成的不是一个单独的“迁移功能”，而是一种新的：

# Elastic Execution Runtime

# 18. 项目的长期研究愿景

本项目希望最终验证一个更加普遍的系统观点：

> **Serverless 的下一阶段，不只是让资源能够动态扩缩，而是让运行中的复杂应用本身具有弹性。**

传统 Serverless 解决：

> “一个应用需要多少资源？”

下一代 Serverless 需要进一步解决：

> **“当资源数量、位置和形态不断变化时，一个正在运行的复杂应用如何持续存在？”**

多模态数据处理是验证这一问题非常合适的场景。

它比传统 Streaming 拥有更加复杂的 Operator 和数据状态，又不像大型同步训练那样强依赖固定的全局执行拓扑，因此为：

**Logical Execution 与 Physical Resource 解耦**

提供了非常有代表性的研究空间。

本合作项目最终希望建立：

> **一种能够主动适应资源变化、在拓扑变化过程中保持执行连续、并允许 Serverless 平台自由重塑底层资源形态的多模态数据执行系统。**

从产品角度，这意味着：

**更高弹性、更快资源回收和更高集群利用率。**

从学术角度，它对应的核心问题则是：

> **如何让一个运行中的复杂 Dataflow 独立于其当前物理执行拓扑，并能够随着资源形态持续演进。**
