英文名称暂定为：**Runtime Topology Reconfiguration and Continuous Migration for Serverless Multimodal Data Processing**

本课题重点研究的不是传统意义上的资源调度或弹性扩缩容，而是：

> **当底层计算资源数量、位置或形态发生变化时，如何对已经运行中的多模态数据处理作业进行执行状态重构和在线迁移，使作业能够在新的资源拓扑上连续执行，而无需整体停止和重新启动。**

# 2. 项目背景

## 2.1 从“资源能够弹性变化”进一步走向“运行中的作业能够随资源变化”

Serverless 云平台的核心目标之一，是根据业务负载动态提供计算资源，从而减少长期资源预留，提高集群整体资源利用率。目前多数弹性技术主要解决的是：
- 根据负载增加或减少计算资源；
- 根据 Operator 特征进行资源调度；
- 通过算子融合减少调度和数据交换开销；
- 通过 Actor Pool 等机制实现计算资源复用和动态扩缩。

这些技术主要回答：

> **一个作业应该使用多少资源，以及资源应该如何高效组织。**

但对于持续数小时甚至数天运行的大规模数据处理作业，仅仅能够调整资源供给仍然不够。

一个正在运行的分布式作业，其 Task、Actor、Partition、中间数据以及运行状态通常已经分散在特定节点之上。当 Serverless 平台因为负载下降、集群资源整理、节点维护或资源回收而需要改变物理资源拓扑时，即使新的资源规模已经足够承载剩余计算，系统仍可能因为已有执行状态绑定在原节点上而无法直接释放资源。

因此容易出现：**业务负载已经下降，但节点无法回收；计算资源已经碎片化，但长作业无法重新聚合；平台具备弹性能力，但运行中的应用本身不具备弹性。**

这成为 Serverless 数据处理进一步提高资源利用率的重要限制。本课题希望研究的核心问题因此不是传统的 Autoscaling，而是：

> **如何使正在运行中的复杂数据处理作业具备随物理资源拓扑变化而持续演进的能力。**

即从：**Resource Elasticity**
进一步走向：**Execution Elasticity**。

# 3. 场景选择：多模态数据处理为什么是该问题的典型场景

本课题选择大规模多模态数据处理作为主要研究对象。典型多模态数据处理流程可能包含：
**数据读取 → 图片/视频解码 → OCR/ASR → VLM/LLM 推理 → Embedding → 数据过滤 → Shuffle/Join → 向量构建 → 数据输出。**

该场景具有几个区别于传统批处理和大模型训练的重要特征。
首先，多模态数据处理通常是**长时间运行的多阶段 Dataflow**。单个作业可能持续数小时甚至更长时间，不同执行阶段的计算量和资源需求变化明显，因此容易在作业运行后期形成大量低利用率节点。
其次，Pipeline 中同时存在**轻量数据处理算子与昂贵 AI 算子**。例如 Decode、Filter 的重计算成本很低，而 VLM、LLM、Embedding 等阶段可能已经消耗大量 GPU/NPU 时间。因此发生资源变化时，简单终止和重新执行会造成较大的重复计算损失。
第三，多模态数据流具有复杂的运行状态。其状态不仅包括传统 Operator State，还可能包括：
- Sample / Block 处理进度；
- Partition 状态；
- Shuffle 中间数据；
- 图片、视频、Tensor 等大对象；
- Object Reference；
- Model/UDF Runtime；
- 已完成的高成本模型推理结果。
因此其迁移问题不能简单退化为传统进程迁移或完整内存快照。

第四，多模态数据处理具有较强的**拓扑可塑性**。与大规模同步训练不同，多模态 Dataflow 通常不要求固定 Worker 数量长期保持不变。同一个逻辑 Pipeline 可以在：**16 个 Worker、8 个 Worker，甚至重新划分后的另一组 Worker**上继续执行。这意味着该场景非常适合研究：

> **Logical Dataflow 与 Physical Execution Topology 解耦。**

多模态数据处理具有传统 Stateful Stream Processing 和大型分布式 AI Training 两类系统的部分特征，但又并不完全属于其中任何一种。它既具有 Dataflow 的 Partition、Shuffle 和执行进度问题，又具有 AI Operator、大对象、异构计算和高重计算成本问题，因此为研究动态资源环境下的连续执行提供了一个具有代表性的研究场景。

> **它既具有 Batch/Dataflow 的大量可重算数据状态，又具有 AI Pipeline 中昂贵的模型执行状态和异构资源依赖。**

近年来相关系统研究已经分别在相邻方向取得进展：ExoFlow 研究了工作流执行与恢复解耦；NSDI'25 的 GRANNY 与 Quicksand 分别研究了细粒度应用迁移和碎片资源利用；VLDB 2026 的 Fugue 研究运行中 Stateful Stream Processing 的在线状态迁移；OSDI'26 的 TrainMover 研究大型训练作业受到中断后的快速恢复；SPADE 则开始研究资源供给持续变化情况下 Batch DAG 的动态调度。

# 4.课题面临的三个关键技术挑战

面向 Serverless 多模态数据处理的动态迁移，并不是简单将一个正在运行的 Actor 或进程从节点 A 搬迁到节点 B。多模态作业运行过程中同时存在处理进度、Operator 状态、Partition、Shuffle 中间结果、大对象引用、模型 Runtime 以及高成本 AI 计算结果等多种状态，这些状态又与具体 Worker、Actor 和数据位置形成复杂依赖。与此同时，Serverless 环境中的资源变化往往意味着 Worker 数量、并行度甚至资源组成发生改变，因此作业需要从执行拓扑 (T_0) 演进到完全不同的 (T_1)，而不是简单完成一对一的节点替换。

## 挑战一：拓扑无关的执行状态解耦与细粒度续作——解决作业“迁得走”

动态迁移首先要解决的并不是“状态怎么搬”，而是**一个已经运行到任意位置的多模态 Dataflow，究竟需要保留哪些状态，才能脱离原有 Worker、Actor 和节点后，在新的资源拓扑上从原有进度继续执行。**

传统进程迁移通常保存进程内存、寄存器等物理运行状态，而传统数据系统 Checkpoint 更多保存 Operator State 或粗粒度执行进度。这两种方式都难以直接适应多模态 Dataflow。多模态作业既包含必须保留的处理进度和高成本 AI 计算结果，也包含大量可以重新计算的临时数据、能够从共享存储重新获得的大对象，以及可以在目标节点重新创建的模型和 UDF Runtime。如果将所有状态完整迁移，会产生很高的迁移成本；如果仅保存粗粒度 Checkpoint，又可能造成大量重复计算。

因此，需要建立一种**与 Worker、Actor 和数据物理位置解耦的 Logical Execution State Model**，从 Dataflow 语义出发描述 Operator、Partition、数据对象、执行进度和 Output Commit 之间的关系，并进一步识别支持作业继续执行所必需的“最小充分状态”。

其核心科学问题是：

> **如何从复杂运行状态中提取支持 Dataflow 正确续作的最小逻辑执行状态，并使其生命周期独立于具体 Worker、Actor 和节点，从而支持执行状态在不同物理拓扑之间重新绑定？**

该问题最终需要形成一套**Topology-independent Execution State & Fine-grained Continuation** 机制。它决定了动态迁移能否摆脱传统进程复制和完整 Checkpoint-Restore，成为真正面向 Dataflow 的执行迁移能力。

---

## 挑战二：低停顿的一致性在线迁移与执行拓扑重构——解决作业“迁得稳”

能够提取执行状态并不意味着已经解决动态迁移。更困难的问题在于：**如何在作业仍然运行、上下游仍然处理数据的过程中，将 Dataflow 从旧执行拓扑 (T_0) 一致地切换到新执行拓扑 (T_1)，同时避免长时间 Stop-the-world。**

例如，当 16 个 Worker 收缩为 6 个 Worker 时，原有 Partition 需要 Merge 和重新映射；当 4 个 Worker 扩展为 12 个 Worker 时，又需要执行 Split。与此同时，旧 Actor 上可能仍然存在正在运行的 Task、尚未消费的数据、正在传输的 Shuffle 数据以及已经产生但尚未提交的结果。迁移过程中，新旧 Actor 还可能短暂共存。

如果缺少严格的一致性协议，就可能产生数据重复执行、数据丢失、状态被多个实例同时修改、上下游路由版本不一致以及已提交结果重复产生等问题。

因此，需要研究一种面向多模态 Dataflow 的 **Non-stop Consistent Reconfiguration Protocol**，使状态准备、Partition Split/Merge、Ownership 转移、Routing Cutover 和 Output Commit 能够协调完成，并将真正需要暂停的时间压缩到很小范围。

其核心科学问题是：

> **如何允许运行中的 Dataflow 在 Worker 数量、并行度和 Partition 布局发生变化时进行在线拓扑重构，同时保证迁移前后数据不丢失、不重复、执行进度一致，并使全局暂停时间尽可能与总状态规模解耦？**

该问题最终对应 **Low-pause Consistent Online Migration**。它决定了动态迁移能否从传统“停止—保存—恢复”模式升级为真正的在线迁移，也是本课题区别于普通 Actor Migration 和 Checkpoint-Restart 的关键技术竞争力。

## 挑战三：计算价值感知的低放大状态迁移与重绑定——解决作业“迁得值”

对于大规模多模态 Dataflow，动态迁移还面临一个非常现实的问题：**能够迁移，并不代表值得迁移。**

不同运行状态的大小和计算价值差异巨大。例如，一个 Decode Buffer 可能很快即可重新生成，将其跨网络迁移反而比重算更昂贵；一个已经完成的 VLM 或 LLM 推理结果虽然数据量并不大，但重新计算可能消耗大量 GPU/NPU 时间，应优先保留；几十 GB 的模型权重虽然很大，却未必应该随着 Actor 一起迁移，而可以在目标节点通过共享 Cache 重新加载；已经位于分布式 Cache 中的大 Tensor 则可能完全不需要搬移，只需要重新建立引用和 Ownership。

因此，动态迁移不能简单等价于 State Copy，而应该针对不同状态，在 **Transfer、Recompute、Reload、Remote Retain、Lazy Fetch 和 Rebind** 等方式之间进行选择。

这使迁移问题进一步演化为一个多目标优化问题，需要同时考虑：

状态大小、网络带宽、数据位置、缓存命中率、模型加载成本、重计算成本、DAG 关键路径、迁移停顿以及节点释放收益。

其核心科学问题是：

> **在满足迁移一致性和资源回收时限的前提下，如何依据状态的计算价值和数据位置，自适应决定哪些状态需要迁移、哪些状态应该重算、哪些状态只需要重新加载或重新绑定，从而最小化数据搬移、执行暂停和重复计算的综合代价？**

该问题最终对应 **Cost-aware Migration, Recompute and State Rebinding**。其目标不是把所有状态都搬走，而是做到：

> **只搬必须搬的状态，只重算值得重算的状态，只重新加载可以低成本恢复的状态。**

这决定了动态迁移在大规模多模态作业中是否真正能够产生净收益，而不是用新的网络和迁移开销替代原有的资源浪费。

> **对于当前资源环境和作业状态，采用哪种状态处置方式能够以最低综合代价完成拓扑变化。**

最终目标是显著降低 **Migration Amplification**，做到“只搬必须搬的状态，只重算值得重算的状态，只重新加载可以低成本恢复的状态”。

前三项研究解决动态迁移本身的核心机制，本部分进一步研究如何利用这些机制解决 Serverless 环境中长作业造成的资源碎片和节点无法及时回收问题。

传统 Autoscaling 更多解决资源供给规模调整问题。当多模态长作业进入尾部阶段后，即使逻辑计算需求已经显著下降，只要剩余 Actor、Partition 或执行状态仍然分散在大量节点上，平台仍无法真正释放这些节点。因此，本研究进一步提出 **Elastic Execution Compaction**：在作业仍持续运行的情况下，对其执行拓扑主动进行重构，将分散的 Logical Execution State 向更少的物理节点重新聚合，从而提前释放完整节点。

从系统角度，希望实现：

**负载变化 → 确定目标资源拓扑 → 运行中状态重构 → 执行状态重新绑定 → 节点释放**

而不是传统的：

**负载变化 → 等待任务结束 → 节点释放。**

该部分重点验证前三项研究能否真正转化为 Serverless 系统收益，主要关注 Reconfiguration Pause、Recomputation Ratio、Migration Amplification、Resource Reclaim Time 和 Cluster Utilization 等指标。

其最终目标不是单纯增加一种“作业迁移功能”，而是建立一种新的 **Elastic Execution Runtime**：

> **资源可以根据业务负载变化，运行中的 Dataflow 也能够随资源形态重新塑造自身执行拓扑。**

## 核心技术链路

四项研究形成从运行时抽象到系统价值的完整技术链路：

**Topology-independent Execution State**  
解决“什么能够迁移和续作”；

↓

**Low-pause Consistent Online Migration**  
解决“运行中的 Dataflow 如何安全迁移”；

↓

**Cost-aware State Migration & Rebinding**  
解决“如何以最低代价完成迁移”；

↓

**Serverless Elastic Execution Compaction**  
解决“如何利用动态迁移实现资源及时回收和利用率提升”。

因此，本课题的技术核心并不是传统意义上的 Checkpoint、Actor Migration 或 Autoscaling，而是研究一种能够让**逻辑执行进度独立于物理执行拓扑，并在运行过程中低成本、一致地重新绑定到底层资源**的新型 Dataflow Runtime。这也是课题相对于传统进程迁移、状态流迁移和简单弹性调度最主要的技术竞争力。

### 年度核心成果汇总

一年合作周期最终形成五类核心成果：**一套总体技术方案、一份系统性技术调研报告、一件具有明确创新点的发明专利、一篇面向系统/数据库顶会的高水平论文，以及一套可运行并可重复实验的动态迁移原型系统代码。**

从阶段关系上，第一阶段解决“**研究什么、为什么值得研究**”；第二阶段重点解决“**迁得走**”；第三阶段进一步解决“**迁得稳、迁得值**”；第四阶段则通过 Serverless 资源压缩和大规模实验回答“**这套动态迁移机制是否真正能够形成系统和产品竞争力**”。

项目验收建议避免以“论文录用”作为一年周期内的硬性条件，而以**完成高质量顶会论文正式投稿、形成完整可重复实验结果和原型系统**作为学术成果验收条件，以降低会议审稿周期对项目验收的不确定性。
