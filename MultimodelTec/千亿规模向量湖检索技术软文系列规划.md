## 第 4 篇：小 TopK 检索与 Lance 深度优化篇

**备选题目：**

- 《10 亿向量小 TopK 延迟从 32 秒降到 0\.47 秒：我们如何对 Lance IO 路径做深度优化》

- 《Lance 不是终点而是起点：向量湖场景下的多级缓存与查询结构下推优化实践》

- 《FabricCache \+ DiskCache \+ 索引下推：千亿向量湖的小 TopK 检索加速三件套》

**摘要：**本文针对 K \< 10000 的小 TopK 检索场景，深入分析 Lance 格式在大规模向量检索下的 IO 路径瓶颈，系统介绍三项核心优化技术：FabricCache 与 DiskCache 协同的多级缓存架构、segment 并行度拆解到 partition 粒度、上层引擎维护索引查询结构并下推给 Lance。通过 10 亿规模 1024 维生产数据的测试验证，检索延迟从 32 秒降至 0\.47 秒，展示引擎与存储格式协同优化的技术深度。

**标签：**小 TopK、Lance 优化、IO 路径、多级缓存、FabricCache、DiskCache、索引下推、性能优化

**核心内容：**

1. **小 TopK 场景定义与瓶颈分析**：K \< 10000 的检索场景，传统方案在 10 亿 1024 维数据下延迟高达 32 秒，瓶颈在 IO 路径

2. **为什么选择 Lance 并深度优化**：Lance 作为列存数据湖格式在向量场景的优势，以及原生 Lance 在大规模检索下的 IO 瓶颈

3. **优化一：多级缓存架构**

    - FabricCache：近计算侧分布式缓存（类似 Alluxio），缓存索引、数据、中间结果，多 worker 共享

    - DiskCache：运行在 Lance 上的本地缓存，充分利用每个 worker 的本地磁盘与内存；预读 \+ 小 IO 合并为 1\~4MB 大 IO，减少远端存储访问

    - 协同策略：DiskCache 负责本地预读与 IO 合并，FabricCache 负责跨 worker 共享热点数据

4. **优化二：segment 并行度拆解到 partition 粒度**：传统按 segment 并行的不足；拆解到 partition 级后并行度大幅提升，小 TopK 场景下长尾延迟显著降低

5. **优化三：索引查询结构下推**：上层 Aura 引擎维护索引查询结构（如 IVF 倒排表的缓存结构）；将缓存的查询结构下推给 Lance，避免 Lance 每次从磁盘重复读取相同的索引元数据；引擎与存储格式协同优化的典型案例

6. **测试验证效果**：10 亿规模 1024 维生产数据，延迟 32 秒 → 0\.47 秒；计划补充 SIFT / DINO 公开数据集 benchmark、QPS 数据、召回率对比

## 第 5 篇：大 TopK 检索优化篇

**备选题目：**

- 《百万级 TopK 如何高效检索？Global Refine \+ Late Read 的分布式协同优化实践》

- 《从小 TopK 到百万 TopK：向量湖检索中两种优化路径的设计与取舍》

- 《粗排剪枝 \+ 延迟读取：大 TopK 场景下如何将 IO 开销降低一个数量级》

**摘要：**本文针对 K 可达 100 万的大 TopK 检索场景（典型应用包括推荐系统召回、多模态粗排等），分析大 TopK 与小 TopK 在优化路径上的本质差异——大 TopK 下候选集巨大，IO 成为主要瓶颈，需要从"减少计算"转向"减少 IO"。详细介绍两项已实现的核心技术：Global Refine（分布式 worker 粗排后协调节点全局剪枝，再精确读取精排）和 Late Read（延迟读取完整向量，多轮剪枝后只读取最终候选集），展示分布式协同优化的工程实现。

**标签：**大 TopK、Global Refine、Late Read、分布式检索、IO 优化、推荐召回、粗排精排

**核心内容：**

1. **大 TopK 场景定义与挑战**：K 可达 100 万，典型场景包括推荐系统召回、多模态粗排、数据去重等；与小 TopK 的优化路径本质不同

2. **为什么大 TopK 不能直接套用小 TopK 优化**：大 TopK 下候选集巨大，IO 成为主要瓶颈，需要从"减少计算"转向"减少 IO"

3. **Global Refine 技术详解**：分布式 worker 先做粗排，将粗排结果汇总到协调节点；协调节点进行全局整理与剪枝，过滤掉不可能进入最终 TopK 的候选；剪枝后再让各 worker 进行精确数据读取与精排；核心收益是大幅减少需要精确读取的数据量

4. **Late Read 技术详解**：延迟读取策略——检索早期只读取向量 ID / 距离等元数据，不读取完整向量；经过多轮剪枝后，只对最终候选集读取完整向量数据；与 Global Refine 的协同关系

5. **分布式协同架构**：基于 Ray 的 worker 调度、协调节点设计、数据 Shuffle 优化

# 技术选型建议

## 增量索引——分块质心方案评估

**结论：方向合理，与 Lance 存储模型天然契合，具备独特竞争力，但需补充质心校准与多 segment 协同机制。**

该方案本质上是 IVF 索引的 segment 级分片变体，优势在于：

- **增量友好**：新 segment 独立建索引，不触动旧数据

- **容错性好**：单 segment 失败不影响全局

- **并行度高**：多 segment 可同时构建

- **与数据湖分区模型一致**：索引构建与数据分区一体化

需关注的风险点：查询时需扫描多 segment 质心，可能增加查询跳转开销；segment 间质心可能重叠，极端情况下影响召回率。建议补充以下技术点：

- segment 质心的定期校准/合并机制

- 查询时多 segment 质心的协同剪枝策略

- 与 Milvus growing/sealed segment 机制的对比分析，突出"与 Lance 深度协同"的差异化

## 索引构建模式——同步 vs 异步选型

**建议：采用"分层准实时索引"架构（类似 LSM\-tree 思想），兼顾写入吞吐与查询实时性，是当前业界最有竞争力的方案。**

架构设计：

1. 新写入数据先进入**内存级实时索引**（如小型 HNSW / 暴力检索），写入即可查

2. 后台异步将内存索引 **flush 并合并** 到 segment 级的大规模磁盘索引（IVF/PQ 等）

3. 查询时同时检索内存索引与磁盘索引，合并结果

核心优势：同时具备高写入吞吐（异步批量构建）、准实时可见（内存索引兜底）、查询性能稳定（大索引走优化路径）。对比纯异步方案（有数据可见延迟）和纯同步方案（写入吞吐受限），综合竞争力最强。
