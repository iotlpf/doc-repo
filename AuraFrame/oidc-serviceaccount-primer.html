OIDC + ServiceAccount
授权原理详解

从"公司访客系统"类比出发，彻底搞懂为什么 ServiceAccount 能替代密钥

01先从一个类比讲起

在深入技术细节之前，我们先用一个生活化的场景建立直觉。

🏢 公司访客系统的故事

假设你在 A 公司上班。你的公司和 B 公司有业务合作，你经常需要去 B 公司的办公楼里开会、用他们的会议室系统。

传统做法（相当于 AK/SK）：B 公司给你发一张他们的门禁卡。但这张卡是长期有效的——如果你离职了、卡丢了、或者被人复制了，B 公司的安全就有风险。而且 B 公司要给每个合作公司的每个人都发卡，管理起来很麻烦。

更聪明的做法（相当于 OIDC 联邦）：

  1. B 公司说："我不用给你们每个人发卡了。我信得过 A 公司的员工身份系统。"
  2. B 公司在自己的安保系统里登记了 A 公司的公章样本（这叫"注册 OIDC Provider"）。
  3. 你要去 B 公司时，A 公司给你开一张临时访客介绍信，上面写着"张三，A 公司员工，工号 12345"，并盖上 A 公司的公章。
  4. 你到了 B 公司前台，出示这封介绍信。B 公司前台核对公章——确实是 A 公司的真章，内容也没被篡改。
  5. B 公司再查一下内部规定："A 公司的张三，允许进入 3 楼会议室"（这叫"Trust Policy 信任策略"）。
  6. 确认无误后，B 公司给你发一张临时门禁卡，有效期 1 天。你用这张临时卡进出 B 公司。
  7. 第二天你再去，A 公司再开一封新的介绍信，B 公司再给你换一张新临时卡。

整个过程中，B 公司从来没有给过你长期门禁卡。你手里只有 A 公司开的介绍信（会过期），以及 B 公司发的临时卡（也会过期）。

这就是 OIDC + ServiceAccount 授权的本质。下面我们把类比中的每个角色对应到技术概念上：

类比中的角色技术中的对应说明
A 公司Kubernetes 集群（或你的云平台）你的工作负载运行的地方
你（员工张三）ServiceAccount工作负载的身份标识
A 公司公章集群的签名私钥（JWKS 中的私钥）只有集群持有，用于签发令牌

02ServiceAccount 到底是什么？

很多人困惑的起点是：ServiceAccount 听起来只是 Kubernetes 里的一个配置对象，它怎么就能用来做认证授权了？

我们分三层来理解：

2.1 第一层：ServiceAccount 是"工作负载的身份证号"

在 Kubernetes 里，人用 User 账号登录（比如 kubectl 用你自己的证书），而程序（Pod）用 ServiceAccount 来标识自己。

你可以把 ServiceAccount 理解为一个纯文本的身份标识，就像"工号 12345"一样。它本身不包含任何密钥，只是一个名字：

# 一个最简单的 ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app-sa        # 这就是"工号"
  namespace: production

Pod 通过 serviceAccountName: my-app-sa 来声明"我是这个身份"。

2.2 第二层：Kubernetes 能为 ServiceAccount 签发"盖章的介绍信"

光有工号没用——你需要一个能证明"我确实是这个工号对应的人"的东西。Kubernetes 集群内置了一个令牌签发服务，可以为任意 ServiceAccount 签发一个 JWT Token。

这个 JWT Token 就是类比中的"盖了公章的介绍信"。关键在于：

  • 它是用集群自己的私钥签名的（相当于盖了公章）；
  • 任何人拿到集群的公钥（通过 OIDC Discovery 端点公开获取），都能验证这个签名是真的、内容没被篡改；
  • Token 里写清楚了"我是谁"（sub = system:serviceaccount:production:my-app-sa）、"谁签发的"（iss = 集群的 OIDC Issuer URL）、"给谁用的"（aud = audience）、"什么时候过期"（exp）。

2.3 第三层：Kubernetes 自动把介绍信放进 Pod 里

这是最关键的一步——你不需要手动申请和分发这个 Token。Kubernetes 通过 Service Account Token Volume Projection（服务账户令牌卷投影）机制，自动把一个短期有效的 JWT Token 挂载到 Pod 内的指定文件路径：

# Pod 启动后，容器内自动出现这个文件
/var/run/secrets/tokens/aura-token

# 文件内容就是一个 JWT（三段式，用 . 分隔）
eyJhbGciOiJSUzI1NiIsImtpZCI6... . eyJpc3MiOiJodHRwczov... . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

这个 Token 默认 1 小时过期，Kubernetes 会自动轮转（在过期前用新 Token 替换文件内容）。你的应用程序只需要读取这个文件就行。

一句话总结

ServiceAccount 本身只是个名字，但 Kubernetes 集群能为它签发带数字签名的短期 JWT 令牌，并自动注入到 Pod 中。这个令牌可以被任何信任该集群的外部系统验证——这就是 ServiceAccount 能用来做认证的根本原因。

03JWT Token 里到底装了什么？

理解了 JWT 的内容，就理解了整个授权机制的核心。JWT 是一个三段式字符串（Header.Payload.Signature），我们重点看中间的 Payload（载荷）部分：

图 2：JWT Token 三段式结构拆解

Payload 中的几个关键字段是整个授权流程的基石：

字段含义在授权中的作用
issIssuer，签发者值是集群的 OIDC Issuer URL。AWS/Aura 通过它判断"这个 Token 是哪个集群签发的"，从而找到对应的公钥来验证签名。
subSubject，主体值是 system:serviceaccount:<namespace>:<name>。这就是"工号"——精确标识了是哪个 ServiceAccount。Trust Policy 就是用这个字段来做精细授权的。
audAudience，受众这个 Token 是发给谁的。比如 "aura" 表示这个 Token 只用于访问 Aura 服务，防止被拿去访问别的系统。
expExpiration，过期时间Unix 时间戳。通常 1 小时后过期。即使 Token 泄漏，攻击者也只有很短的窗口期。
iatIssued At，签发时间Token 是什么时候签发的，用于判断是否新鲜。
重要理解

JWT 的 Payload 是Base64 编码，不是加密！任何人都能解码看到里面的内容。它的安全性靠的是签名——你能读，但你改不了，因为改了之后签名就对不上了。这就像介绍信的内容是公开的，但公章你仿造不了。

04完整流程拆解（7 步走）

现在我们把所有零件拼起来，看一次完整的授权调用是怎么发生的。我们以 AWS IRSA 为例（Aura 的方案完全同构）。

1

建立信任：注册 OIDC Provider

管理员在 AWS IAM 中注册 EKS 集群的 OIDC Issuer URL。AWS 自动访问该 URL 的 /.well-known/openid-configuration 和 /keys（JWKS）端点，获取集群的公钥并保存。这一步相当于"B 公司留存 A 公司的公章样本"。这是一次性操作，之后所有该集群的 Token 都能被验证。

2

定义角色与信任策略：创建 IAM Role

管理员创建一个 IAM Role（比如 data-processor-role），配置两件事：Permission Policy（这个角色能访问哪些 AWS 资源）和 Trust Policy（谁能扮演这个角色）。Trust Policy 中写明："只有 OIDC Issuer = 我的EKS集群，且 sub = system:serviceaccount:production:my-app-sa 的 Token，才能扮演我。"这相当于"B 公司的内部准入规定"。

3

绑定身份：给 ServiceAccount 标注 Role ARN

管理员在 Kubernetes 的 ServiceAccount 上添加注解 eks.amazonaws.com/role-arn: arn:aws:iam::123:role/data-processor-role。这相当于告诉集群："使用这个 ServiceAccount 的 Pod，应该去扮演那个 IAM Role。"

4

自动注入：Pod 启动时获得 Token 和环境变量

Pod 调度到节点上启动时，EKS 的 Pod Identity Webhook（一个 Mutating Admission Webhook）自动做两件事：(a) 把一个短期 JWT Token 通过 projected volume 挂载到 /var/run/secrets/eks.amazonaws.com/serviceaccount/token；(b) 注入两个环境变量 AWS_ROLE_ARN 和 AWS_WEB_IDENTITY_TOKEN_FILE。用户的 Pod YAML 里完全不需要写这些。

5

交换凭证：SDK 调用 STS AssumeRoleWithWebIdentity

用户代码初始化 AWS SDK 时（AwsClient.builder().build()，无任何凭证参数），SDK 的 Credential Provider Chain 检测到 AWS_WEB_IDENTITY_TOKEN_FILE 环境变量，于是：读取 Token 文件 → 调用 sts:AssumeRoleWithWebIdentity API，传入 JWT Token 和 Role ARN。

6

验证与签发：STS 验证 Token 并返回临时凭证

AWS STS 收到请求后做三件事：(a) 根据 Token 的 iss 找到已注册的 OIDC Provider，用其公钥验证 JWT 签名（确认是真的、没被篡改）；(b) 检查 exp 没过期、aud 匹配；(c) 检查目标 Role 的 Trust Policy 是否允许这个 sub 扮演。全部通过后，STS 签发一组临时 AK/SK + Session Token（默认 1 小时有效），返回给 SDK。

7

使用与自动刷新：SDK 缓存并自动续期

SDK 缓存临时凭证，后续所有 AWS API 请求都用这组临时凭证签名。当凭证剩余有效期不到 20%（约 12 分钟）时，SDK 自动重新读取 Token 文件（K8s 已经自动轮转了新 Token），再次调用 STS 换取新凭证。整个过程对用户代码完全透明。

05为什么 ServiceAccount 能搞定这件事？

这是最核心的问题。ServiceAccount 看起来只是 K8s 里的一个 YAML 对象，它凭什么能替代 AK/SK 这种"真正的密钥"？答案在于它同时具备了四个关键特性，缺一不可：

5.1 特性一：集群能为它签发可验证的签名令牌

ServiceAccount 本身只是名字，但 Kubernetes 集群持有一对非对称密钥（私钥在集群内部，公钥公开）。集群能用私钥为任意 ServiceAccount 签发 JWT，外部系统能用公钥验证签名。这是整个体系的密码学根基——没有这个，ServiceAccount 就只是个可以随便伪造的字符串。

类比：公章（私钥）+ 公章样本（公钥）

5.2 特性二：令牌是短期的、自动轮转的

Projected Service Account Token 默认 1 小时过期，Kubernetes 的 kubelet 会在 Token 过期前自动用新 Token 替换挂载文件。这意味着：

  • 即使 Token 被窃取（比如日志泄露、容器逃逸），攻击者最多只有 1 小时的窗口期；
  • 不需要人工轮转，不存在"忘了换密钥"的问题；
  • Token 永远不会被硬编码到代码或镜像中。

类比：介绍信每天重新开，旧的自动作废

5.3 特性三：令牌包含精确的身份声明

JWT 的 sub 字段精确到 namespace:serviceaccount 级别，这使得授权可以做到工作负载粒度——而不是"整个集群共享一个身份"。你可以定义："只有 production 命名空间下的 data-processor 这个 SA 能访问数据处理资源，其他 SA 不行。"

这比传统的"整台机器挂一个 IAM Role"（EC2 Instance Profile）精细得多——在同一个 Node 上运行的不同 Pod 可以有完全不同的权限。

类比：介绍信上写了具体工号，不是" A 公司员工"这种模糊身份

5.4 特性四：令牌自动注入，零分发成本

通过 Kubernetes 的 Token Volume Projection + Admission Webhook，JWT Token 和环境变量是在 Pod 创建时自动注入的。开发者不需要：

  • 手动创建密钥；
  • 把密钥放到 Secret 里；
  • 在 Deployment 里挂载 Secret；
  • 在代码里读取密钥。

只需要在 ServiceAccount 上加一行注解，剩下的全自动化。这就是为什么用户能"只关注授权，不关注密钥"。

类比：员工入职时工牌自动发，不用自己去申请

06信任关系是怎么建立的？

理解了流程之后，还有一个关键问题：AWS（或 Aura）凭什么相信一个来自 Kubernetes 的 JWT？这就涉及到信任链的建立。

6.1 信任链的三层结构

  1. 第一层：OIDC Provider 注册（集群级信任）
    管理员在 AWS 中注册集群的 OIDC Issuer URL，AWS 获取并保存集群的公钥。这建立了"我信任这个集群签发的所有 Token 的签名"。但这只是信任了签发者，还没信任具体身份。
  2. 第二层：Trust Policy（身份级信任）
    IAM Role 的 Trust Policy 精确指定"只有这个集群的这个 ServiceAccount（sub）能扮演我"。这建立了"我信任这个具体身份来扮演这个角色"。
  3. 第三层：Permission Policy（权限级授权）
    IAM Role 的 Permission Policy 指定"这个角色能访问哪些资源、执行哪些操作"。这是实际的权限边界。
三层信任的类比

第一层 = "我认可 A 公司的公章是真的"；第二层 = "A 公司的张三这个人可以进我们公司"；第三层 = "张三可以进 3 楼会议室，但不能进 5 楼机房"。三层缺一不可，层层收窄。

6.2 为什么不需要把密钥给 AWS？

这是 OIDC 联邦最精妙的地方：整个过程中，Kubernetes 集群的私钥从来没有离开过集群，AWS 也从来没有持有过集群的私钥。AWS 只持有公钥——而公钥本来就是公开的，不怕泄漏。

验证签名只需要公钥（数学上：私钥签名，公钥验证，公钥无法推导出私钥）。这就是非对称密码学的威力——信任建立在"我能验证你"之上，而不是"我持有你的密钥"之上。

07常见疑问解答

JWT Token 是挂载到容器里的文件，别人进了容器不就能读到吗？
是的，如果攻击者已经进入了容器（比如通过 RCE），确实能读到 Token 文件。但这和 AK/SK 被偷是一样的风险。关键区别在于：JWT 1 小时就过期了，而 AK/SK 可能长期有效。而且 K8s 的 projected token 支持 audience 限制——这个 Token 只能用于访问 Aura，不能拿去访问别的系统。另外，你可以通过 Pod Security Policy / Seccomp 等手段限制容器内的访问。
如果 Kubernetes 集群本身被攻破了呢？
如果集群的签名私钥被窃取，攻击者可以伪造任意 ServiceAccount 的 Token。这是 OIDC 联邦模式的根本信任边界——你必须信任集群的安全性。这和"如果你公司的公章被盗，别人就能伪造介绍信"是一个道理。缓解措施包括：集群私钥使用 KMS 托管、定期轮换、限制 OIDC Provider 的注册范围、监控异常的 AssumeRole 行为。
ServiceAccount 的 JWT 和传统的 ServiceAccount Secret 有什么区别？
Kubernetes 早期版本中，ServiceAccount 会自动创建一个长期有效的 Secret（包含 CA 证书和 Token），这个 Token 不过期。这是不安全的。Projected Service Account Token（K8s 1.12+ 引入，1.20+ 成为推荐方式）是短期的、带 audience 的、自动轮转的，并且是通过 TokenRequest API 动态签发的，不是存在 etcd 里的静态 Secret。IRSA 使用的正是这种 projected token。
为什么不直接用 ServiceAccount 的 Token 调用 Aura，还要多一步 STS 交换？
两个原因：(1) JWT Token 的 audience 是固定的（比如 "aura"），它只能证明"我是谁"，但不包含"我能做什么"的权限信息。STS 交换的过程就是把"身份证明"换成"带权限的访问凭证"——这一步中 Trust Policy 决定了你能获得什么权限。(2) Aura 的服务端可能使用 AK/SK 签名协议（如 SigV4）来认证请求，而不是直接接受 JWT。STS 把 JWT 转换成服务端能直接验证的临时 AK/SK + Session Token，保持了服务端认证协议的统一。
本地开发时没有 Kubernetes，怎么用 OIDC？
本地开发场景不使用 OIDC 联邦，而是使用 AK/SK 模式（SDK 自动轮转）或证书联邦模式。OIDC Workload Identity 专门针对"工作负载运行在支持 OIDC 的平台上"的场景。这就是为什么 Aura SDK 需要 Provider Chain——在云上自动用 OIDC Provider，在本地自动用 Profile Provider，用户代码不变。
GCP 和 Azure 也是同样的原理吗？
是的，原理完全一致，只是术语和实现细节不同。GCP Workload Identity 把 K8s SA 映射到 GCP Service Account，底层也是 OIDC；Azure Workload Identity 把 K8s SA 关联到 Entra ID Application，通过 federated credential 建立信任，同样是 OIDC JWT 交换访问令牌。三大云厂商在 2019-2023 年间全部收敛到了这个模式。

08一句话总结

🎯 核心结论

ServiceAccount 能替代密钥，不是因为它本身是密钥，而是因为：

  1. Kubernetes 集群能为它签发带数字签名的短期 JWT 令牌（相当于盖了公章的介绍信）；
  2. 外部系统（AWS/Aura）通过注册 OIDC Provider 获得集群的公钥，从而能验证令牌真伪（相当于留存了公章样本）；
  3. 外部系统通过 Trust Policy 精确控制"哪个 ServiceAccount 能获得什么权限"（相当于内部准入规定）；
  4. STS 把"身份证明（JWT）"交换为"临时访问凭证（AK/SK）"（相当于前台换发临时门禁卡）；
  5. 整个过程自动化、短期化、精细化，用户代码中永远不需要出现长期密钥。

记住这个类比：ServiceAccount = 员工工号，JWT = 盖了公章的临时介绍信，OIDC Provider 注册 = 留存公章样本，Trust Policy = 准入规定，STS = 前台换临时卡，临时 AK/SK = 临时门禁卡。
